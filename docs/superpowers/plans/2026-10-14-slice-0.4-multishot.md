# Slice 0.4 Multi-Shot + Organ Tags Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `POST /identify` accepts 1–5 photos, each tagged with an organ, validates the whole set on both sides before spending a Pl@ntNet credit, persists one `identification_images` row per photo (submitted organ + predicted organ), and the Flutter Capture screen lets the user add up to 5 shots, tag each, and remove any. The backend response carries full per-photo info; the UI shows only what it showed in 0.3 (first photo, organ banner naming the photo).

**Architecture:** The 0.3 service layer is extended, not restructured. `image_validation` gains set-level rules (`validate_set_shape`, `validate_image_set`). `plantnet_client.identify` takes a list of `ImagePart`s and sends repeated `images`/`organs` fields. `persist_identification` takes a list of `StoredImage`s and maps `predictedOrgans` to photos by position. The router orchestrates validate-set → Pl@ntNet → upload each → persist, all-or-nothing. On the client, `PhotoShot` (photo + organ) replaces the bare `PickedPhoto` in the repository; the Capture screen holds a list of shots. **No migration**: `identification_images` already has every column.

**Tech Stack:** unchanged from 0.3 (FastAPI, Pillow, boto3, httpx/respx; Flutter web, `file_picker` 13, `image` dev dep; Playwright; podman compose).

**Spec:** `docs/superpowers/specs/2026-10-14-web-mvp-design.md` (slice 0.4 row, "Data flow", "Error handling", "Testing"). Also read `docs/plantnet-api.md` (identify request rules), `docs/superpowers/plans/2026-10-14-slice-0.3-identify.md` (whose code this plan modifies), and `docs/architecture.md` ("Identify request flow", "Data model").

## Context

Slice 0.3 ships a single-photo flow: multipart field `image`, organ fixed to `auto`, response `image: {...}`. Its code is the starting point: `backend/app/services/{image_validation,plantnet_client,storage,identifications}.py`, `backend/app/routers/identify.py`, `backend/app/schemas/identify.py`, the client's `ApiClient.postMultipart`, `IdentifyOutcome`, `IdentifyRepository`, `PickedPhoto`, `PhotoPicker`, the Capture/Results screens, and `e2e/tests/identify.spec.ts`.

Done when (spec): **invalid sets are rejected on both sides, and organ feedback is visible.** In addition (user request): **a real-Pl@ntNet smoke test with a multi-photo set passes as the final gate** (Task 8, Step 5).

Decisions confirmed with the user:
- **Capture UI: add one photo at a time** (existing "choose photo" button), up to 5, each shot with an organ selector and a remove (×) control. No multi-select picker.
- **The response returns full per-photo info, but the UI keeps showing only what it shows today** (first photo preview + the organ banner). What else to show is decided later.

Decisions taken here (defaults, not asked):
- **Breaking API change, no compatibility shim:** `image` → repeated `images`; new repeated `organs` (matched by position); response `image` → `images[]`. Nothing is released, and the only consumers are the Flutter client and e2e, both updated in this plan.
- **Allowed organs:** `auto`, `leaf`, `flower`, `fruit`, `bark` (docs/plantnet-api.md). Pl@ntNet may *predict* others (e.g. `habit`); predictions are stored as plain strings.
- **Total size cap 50,000,000 bytes** (Pl@ntNet's per-request limit, per docs) on top of the 10 MiB per-photo cap, because 5 × 10 MiB = 52.4 MB would exceed it. Over-size is 413, mirrored on the client when adding a shot.
- **Error messages name the photo** (`Photo 2: Photo must be at least 800x800 …`), 1-based by upload order. The client's own rejections name the file instead (`leaf.png: …`), since it knows the name.
- **Repeated form fields on the client:** `package:http`'s `MultipartRequest.fields` is a `Map` and cannot repeat a key, so each organ is sent as a text part built with `MultipartFile.fromString('organs', value)` (no filename → Starlette parses it as a form field). Task 7's Playwright run is the end-to-end proof of this.
- **Banner:** "We detected a *flower* in photo *N*", using the first photo that has a predicted organ (hidden if none).
- **Predicted organs map by position.** If Pl@ntNet returns fewer predictions than photos, the rest are stored as `NULL` instead of failing the request.
- **Branch:** `phase0/slice-0.4-multishot`, cut from `phase0/slice-0.3-identify` (not yet merged anywhere). Per the user, this line of work never merges into `main`; the user does the pushing and PRs.

5. **Repeated multipart fields really arrive.** The client sends N `organs` parts that the server reads as a list in order. Pinned in Task 5 (body contains `name="organs"` N times) and proven end to end in Task 7.

MAX_IMAGES = 5
# Pl@ntNet rejects requests over 50 MB; five photos at the 10 MiB per-photo cap would exceed it.
MAX_TOTAL_BYTES = 50_000_000
ORGANS = ("auto", "leaf", "flower", "fruit", "bark")

```python
def validate_set_shape(n_images: int, organs: list[str]) -> None:
    """Cheap checks on counts and organ tags; run before reading any file body."""
    if n_images < 1:
        raise ImageRejected("Add at least one photo")
    if n_images > MAX_IMAGES:
        raise ImageRejected(f"At most {MAX_IMAGES} photos per identification")
    if len(organs) != n_images:
        raise ImageRejected(
            f"Got {n_images} photo(s) but {len(organs)} organ tag(s); send one organ per photo"
        )
    for i, organ in enumerate(organs, start=1):
        if organ not in ORGANS:
            raise ImageRejected(
                f"Photo {i}: unknown organ {organ[:20]!r} (use one of: {', '.join(ORGANS)})"
            )


def validate_image_set(files: list[bytes], organs: list[str]) -> list[ValidatedImage]:
    validate_set_shape(len(files), organs)
    if sum(len(f) for f in files) > MAX_TOTAL_BYTES:
        raise ImageRejected("Photos total more than 50 MB", status_code=413)
    validated = []
    for i, data in enumerate(files, start=1):
        try:
            validated.append(validate_image(data))
        except ImageRejected as e:
            raise ImageRejected(f"Photo {i}: {e.message}", status_code=e.status_code) from None
    return validated
```

class FakeStorage:
    def __init__(self, error: Exception | None = None, fail_after: int | None = None):
        self.error = error
        self.fail_after = fail_after
        self.objects: dict[str, tuple[bytes, str]] = {}

    def put(self, key: str, data: bytes, content_type: str) -> None:
        if self.error is not None and (
            self.fail_after is None or len(self.objects) >= self.fail_after

  /// Multipart POST. [fields] may repeat a key (MultipartRequest.fields is a Map and cannot),
  /// so each one is sent as a text part with no filename, which servers read as a form field.
  Future<Map<String, dynamic>> postMultipart(
    String path, {
    required List<UploadPart> files,
    List<MapEntry<String, String>> fields = const [],
    String? token,
    Duration? timeout,
  }) =>
      _send(
        () async {
          final req = http.MultipartRequest('POST', _uri(path));
          for (final f in files) {
            req.files.add(http.MultipartFile.fromBytes(f.field, f.bytes, filename: f.filename));
          }
          for (final f in fields) {
            req.files.add(http.MultipartFile.fromString(f.key, f.value));
          }
          if (token != null) req.headers['Authorization'] = 'Bearer $token';
          return http.Response.fromStream(await _http.send(req));
        },
        authenticated: token != null,
        timeout: timeout,
      );
