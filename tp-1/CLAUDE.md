## About this app

A form for filing complaints about the Buenos Aires Subte (subway). The assignment's real point is UI/UX: build a normal, working form first, then deliberately degrade its usability to study heuristics and anti-patterns. The "make it annoying" pass has started (see "Anti-patterns" below) — not every field is broken yet, so don't assume the whole form is fair game for friction without being asked.

## Architecture

Kept intentionally minimal — this is a front-end-only TP with no backend, and as of the single-file migration, no separate CSS/JS files either:

- `index.html` — everything: form markup, all styling in an inline `<style>` block (plain CSS, no preprocessor, no framework), and all behavior in an inline `<script>` block (vanilla JS, no build step, no bundler, no dependencies). This is a deliberate constraint the user asked for ("tendría que ser un html single file") — keep all future markup/CSS/JS changes inside this one file rather than splitting them back out, unless the user says otherwise.
- No local asset files. The Subte logo is loaded directly from Wikimedia Commons at `https://upload.wikimedia.org/wikipedia/commons/b/bf/Subte-logo.svg` (`<link rel="icon">` and the header `<img>`) rather than a repo-local file or a base64 data URI — the user explicitly chose the live external URL over inlining, after weighing that it makes the page dependent on Wikimedia's availability. There used to be a repo-local `assets/subte.png`; it was deleted once the header switched to the Wikimedia URL.

Submissions are simulated: on valid submit, the inline script generates a ticket number, builds a plain-language summary of every field the user entered (`buildConfirmationSummary()`, rendered into the `<dl id="confirmation-summary">`), and shows both in the confirmation message — this summary is a straightforward usability feature, not one of the anti-patterns below. There is no backend and no network call except the one Wikimedia image fetch above. If persistence across reloads is ever wanted, use `localStorage` rather than adding a server — stay within the "front-end only" constraint unless the user says otherwise.

**Verifying UI changes**: this environment has no `chromium-cli`/Playwright, but `chromium-browser --headless --disable-gpu --no-sandbox --screenshot=<path> --window-size=<W>,<H> <url>` is installed and works — use it (with `python3 -m http.server -d tp-1 <port>` serving the folder) to actually check rendering after visual changes, instead of settling for static syntax/HTTP checks. For anything that needs *interaction* (typing, clicking) rather than a static load, launch with `--headless=new --remote-debugging-port=<port>` instead, then drive it over CDP: `GET http://localhost:<port>/json` to find the page target's `webSocketDebuggerUrl`, open a `WebSocket` to it (Node 22's built-in `WebSocket` works fine, no dependency needed), send `Runtime.evaluate` to mutate the DOM/dispatch events, and `Page.captureScreenshot` to capture the result. Wait out any CSS `transition` duration before capturing, or the screenshot catches a mid-transition frame instead of the true end state.

## Branding

Line colors follow the real Buenos Aires Subte signage/wayfinding system (see `--line-*` custom properties in `index.html`'s inline `<style>`): A light blue, B red, C navy, D green, E violet, H yellow, Premetro orange. The "Línea" field is a set of clickable colored spheres (radio inputs styled as circular badges) rather than a plain `<select>`, echoing the line-colored porticos described in the real signage system.

The real Subte logo is loaded live from Wikimedia Commons (`https://upload.wikimedia.org/wikipedia/commons/b/bf/Subte-logo.svg`, the file linked from the [Subterráneos de Buenos Aires Wikipedia article](https://es.wikipedia.org/wiki/Subterr%C3%A1neos_de_Buenos_Aires)) and used in `.site-header` (a full-width bar at the top of `index.html`, above `.page`), styled after GCBA's (Gobierno de la Ciudad de Buenos Aires) look: white header background, a bold black "Buenos Aires Ciudad"-style eyebrow + heading, and a thin yellow accent bar under the header. `--color-brand-yellow` (`#f6cd19`) and `--color-brand-black` (`#111111`) in `index.html`'s inline `<style>` were originally sampled from a since-deleted local copy of this same logo (via a one-off PIL pixel sample) rather than guessed — reuse those tokens for anything meant to read as "official" GCBA branding, and keep them separate from `--line-h` (a similar but distinct yellow with different meaning — line color, not brand color). The submit button is black with yellow text, matching the black CTA pattern common on GCBA microsites.

## Form fields (current)

- Subte line (A–H, Premetro) — colored sphere picker
- Station — one-per-row list, all 83 stations across every line, order shuffled, each row a toggle switch (only one can be on at a time)
- Date/time of the incident — custom stepper (no calendar, no typing), defaults to 25 May 1810, moves ±1 second per arrow click
- Complaint type (delay, cleanliness, security/safety, accessibility, staff conduct, other) — picked by playing a slingshot ball-toss mini-game into one of six labeled baskets
- Description (free text) — background darkens toward black as you type, text becomes unreadable by ~char 10
- Reporter first name and last name — two dropdowns, 500 procedurally-generated random entries each, reshuffled on every load/reset; email (multi-tap phone keypad), phone (optional, entered as raw binary/BCD)

## Anti-patterns

Introduced deliberately as part of the "make it annoying" pass. Each entry: what it is, which heuristic it violates, why.

- **Line picker as bouncing bubbles** (`.line-picker--bubbles` in `index.html`'s inline `<style>`; `initLineBubbles()` in `index.html`'s inline `<script>`). The line spheres no longer sit still in a row — they're absolutely positioned inside a fixed-size rectangle and animated every frame via `requestAnimationFrame`, starting at a random position with a random velocity and bouncing off the rectangle's edges like a screensaver, forever. Selecting a line means clicking a target that is actively moving away from the cursor. The radio/label semantics are unchanged (still a real `role="radiogroup"` of labeled radio inputs), so it remains technically operable, just harder in practice — fast bubbles or unlucky timing can require several attempts. Violates Nielsen heuristic #7 (efficiency of use — a moving target is strictly harder to acquire than a static one, for every user) and is especially bad for heuristic #5/accessibility: motor-impaired users and anyone using switch/head-pointer input may not be able to click a moving target at all, and the constant motion is also a vestibular/motion-sensitivity concern (no `prefers-reduced-motion` handling).
- **Complaint type picked via a ball-toss mini-game** (`CLAIM_TYPES`, `claimBaskets`, `updateClaimBallPhysics()`, `resolveClaimCatch()`/`resolveClaimMiss()`, `resetClaimGame()` in `index.html`'s inline `<script>`; `.claim-game`/`<canvas id="claim-game-canvas">` in the markup and inline `<style>`). "Tipo de reclamo" is no longer a `<select>` — it's a `<canvas>`-based slingshot game: the user drags the ball backward (away from six labeled baskets — Demora, Limpieza, Seguridad, Accesib., Personal, Otro) and releases to launch it under simple gravity physics. Landing in a basket sets that complaint type; missing sets nothing. Either outcome ends the throw and disables further dragging (`if (claimBall.launched) return;` in the `pointerdown` handler) until the **Reiniciar** button is pressed — even to change an already-successful catch, the whole throw must be redone. Violates Nielsen heuristic #7 (efficiency of use — a physics-aiming task takes far longer and more attempts than clicking a dropdown option) and #6 (recognition-over-recall doesn't even apply cleanly here: the "control" itself demands motor precision, not recall, which is arguably worse for accessibility) — also a hard accessibility failure (Nielsen #1/#5 territory): there is no keyboard-operable path at all, since the whole mechanic is pointer-drag-and-release, so keyboard-only and switch-input users cannot complete this field.
- **Email typed via a multi-tap phone keypad** (`KEY_CHARS`, `pressKeypadKey()`, `KEYPAD_TAP_TIMEOUT_MS` in `index.html`'s inline `<script>`; `.phone-keypad` in `index.html`'s inline `<style>`). The Email field is no longer a text `<input>` — it's a 12-button numeric keypad (1–9, 0, delete) styled after pre-smartphone feature phones, using the real per-key letter groups (`2`=abc, `3`=def, `4`=ghi, `5`=jkl, `6`=mno, `7`=pqrs, `8`=tuv, `9`=wxyz, `0`=space, `1`=`. @ _ -` for the symbols an email actually needs). Typing a letter means tapping its key repeatedly within an 800ms window to cycle to the right letter (e.g. "c" = tap `2` three times), and tapping a different key (or waiting out the window) commits the current character and starts the next one — the exact multi-tap input method phones used before T9/smartphones. Violates Nielsen heuristic #6 (recognition rather than recall — the user must remember or re-derive which tap-count maps to which letter) and #7 (efficiency of use — entering even a short email address takes many more physical taps than typing it, and a mistimed tap silently advances the cycle instead of committing).
- **Phone entered as raw binary (BCD) instead of digits** (`decodeBcdNibble()`, `renderBinaryPhone()`, `phoneBits` in `index.html`'s inline `<script>`; `.binary-phone` in the inline `<style>`). The optional "Teléfono" field has no digit input at all — only two buttons, `0` and `1`, plus a delete key. Every 4 bits typed is grouped and decoded as one BCD (binary-coded decimal) nibble into a decimal digit (`0000`–`1001` → `0`–`9`); the running bit string and the live-decoded "Resultado" are both shown as the user taps. A single invalid nibble (`1010`–`1111`, patterns BCD doesn't use) doesn't just fail to decode itself — it blanks the *entire* decoded phone number back to nothing (shown as e.g. `15?` in the display, but the hidden field submitted is empty), so one mistyped bit near the end of a long number destroys everything typed before it. Violates Nielsen heuristic #5 (error prevention — there's no cheaper way to enter a decimal phone number than reciting it in binary) and #9 (help recognize/recover from errors — the `?` shows something went wrong but not where, and the "fix" is retyping the whole number rather than the one bad nibble).
- **Station picker as a shuffled, one-at-a-time toggle list** (`STATIONS_BY_LINE`, `renderStationList()`, `handleStationToggle()` in `index.html`'s inline `<script>`; `.station-grid`/`.station-row`/`.toggle-switch` in `index.html`'s inline `<style>`). All 83 stations from every line are flattened into one list, shuffled with Fisher-Yates on every render (initial load and every "Cargar otro reclamo" reset — the order never repeats), rendered one per row with no grouping by line and no alphabetical order, each with a toggle switch instead of a single-click option. The user just picked their line one field above, but that choice is not used to filter or sort the station list — finding a station means scanning the whole shuffled list instead of a short, line-scoped list. Violates Nielsen heuristic #6 (recognition rather than recall / minimize memory load) and #7 (flexibility and efficiency of use — no shortcut for "I already told you my line").
- **Toggle switch that blocks itself** (`handleStationToggle()` in `index.html`'s inline `<script>`). Turning one station's toggle on disables every other toggle in the list — to pick a different station you must first flip the current one back off, then scroll/search again and flip the new one on. A toggle switch visually signals "independent on/off control," but here it behaves like a single-select radio with an extra mandatory step, breaking the control's own affordance. Violates Nielsen heuristic #2 (match between system and the real world — a toggle should mean what a toggle means) and adds pure friction to what should be a one-click change.
- **Datetime stepper defaulting to 1810, ±1 second at a time** (`DEFAULT_INCIDENT_DATETIME`, `adjustDateTime()`, the `#datetime-up`/`#datetime-down` buttons in `index.html`'s inline `<script>`). There's no calendar, no typing, no way to jump — only two arrows, each moving the incident datetime by exactly one second, and the default value is the Revolución de Mayo (25/05/1810), roughly 216 years before any real incident could have happened. Reaching the present by clicking one-second increments is not practically possible (~6.8 billion clicks). Violates Nielsen heuristic #7 (efficiency of use — no way to jump to "now" or even to today) and #1 (visibility of system status is technically preserved — the display updates — but the *scale* of the control is wildly mismatched to the task, so the visible feedback doesn't translate into reachable progress).
- **Name/surname as 500-entry random dropdowns** (`generateWords()`, `renderNameDropdown()` in `index.html`'s inline `<script>`). "Nombre" and "Apellido" are no longer free-text — each is a `<select>` populated with 500 procedurally-generated, unique, Spanish-sounding-but-fake words (prefix+suffix combinations), reshuffled every load/reset. The reporter's actual name is not among the options — the field asks for something that provably cannot be entered correctly. Violates Nielsen heuristic #5 (error prevention — the form structurally cannot capture correct data) and #6 (recognition rather than recall — nothing in the list is recognizable, because none of it is real).
- **Dead link offering a fake escape hatch** (`data-dead-link` in `index.html`, the click listener in `index.html`'s inline `<script>`). Directly under the name/surname dropdowns, a real-looking hyperlink reads "¿No está tu nombre o tu apellido? ¡Llená este formulario para solicitar que lo agreguemos!" — styled exactly like the app's other links, but the click handler calls `event.preventDefault()` and does nothing. It's the one place in the form that *acknowledges* the previous anti-pattern (your name probably isn't in the list) and offers a fix, then the fix doesn't exist. Violates Nielsen heuristic #9 (help users recognize and recover from errors — this actively simulates a recovery path with no recovery behind it) and is a textbook dark pattern (a fake affordance) rather than a heuristic slip.
- **Description field that darkens itself into illegibility** (`updateDescriptionDarkness()` in `index.html`'s inline `<script>`, `#description` transition in `index.html`'s inline `<style>`). The textarea's background ramps from near-white down to *the exact color of `--color-text`* (`hsl(213, 13%, 14%)` / `#1f2328`) over exactly 10 characters (`DESCRIPTION_DARKEN_PER_CHAR = (96 - 14) / 10 = 8.2` lightness points/char, same hue/saturation as the text throughout so the ramp doesn't hue-shift at the end); once the floor is hit the background is set to the literal `var(--color-text)` (not a reconstructed `hsl()` guess) so there's zero rounding drift — background and text are pixel-identical, confirmed via `getComputedStyle` (`backgroundColor` and `color` both `rgb(31, 35, 40)` at 10 chars) in the CDP verification script, not just eyeballed. Deleting characters lightens it back up (recomputed from current length on every `input` event, not a one-way ratchet). Violates Nielsen heuristic #1 (visibility of system status — the one piece of status that matters, "what did I just type," is the one thing hidden) and is really a self-inflicted contrast/accessibility failure (WCAG 1.4.3, taken to its logical extreme: 1:1 contrast) rather than a workflow inefficiency.
